# PYTHIA: архитектура и модель данных (черновик)

Oct 14, 2026 · @Anastasia

## Цель и рамки

К демо делаем отдельное веб-приложение PYTHIA, где Seek wisdom и Share wisdom работают по-настоящему: живой LLM через шлюз SecondStack, настоящая база и поиск по смыслу. Expertise, Discoveries и Pantheon считаются из тех же данных, а компанию наполняем правдоподобными синтетическими данными.

| Экран | Что работает по-настоящему | Что упрощаем на хакатоне |
| --- | --- | --- |
| Seek wisdom | Голос или текст, разбор запроса, поиск решений, экспертов и коллег, одна рекомендация от Пифии | Написать эксперту = уведомление внутри PYTHIA, без почты и Teams |
| Share wisdom | Извлечение навыков, опыта и решений, правка, Save & share, кому пригодится | Проверка на дубли простая, по схожести |
| Build it with Pythia | Уточняющие вопросы и черновик спецификации скилла или агента | Скилл создаётся по-настоящему и доступен через наш MCP; публикация в Cowork — если найдём API |
| Expertise | Профиль из подтверждённых и найденных навыков, поиск людей | Без интеграции с HR-системой |
| Discoveries | Кластеры повторяющихся запросов, команды, оценка часов | Пересчёт по кнопке или раз в N минут, не в реальном времени |
| Pantheon | Рейтинг из журнала вкладов и благодарностей | Формула очков простая и прозрачная |

Главный принцип: всё, что видно на демо, считается из базы, а не нарисовано. Синтетика нужна только чтобы базе было что искать.

## Архитектура

PYTHIA — одно Next.js-приложение (интерфейс и API вместе) с одной базой Postgres. Свою модель мы не держим: чат-модель, эмбеддинги и распознавание речи берём из шлюза SecondStack, вход — через его SSO. Так PYTHIA честно «построена на SecondStack», но не зависит от его интерфейса.

MCP-сервер делаем точно: через него Пифию и созданные ею скиллы можно использовать прямо из чата SecondStack. Пунктиром — публикация скилла напрямую в Cowork Agent, если у SecondStack найдётся для этого API.

| Слой | Выбор | Почему |
| --- | --- | --- |
| Интерфейс | Next.js + React + Tailwind | Макет уже на HTML/CSS, переносится почти один в один |
| Сервер | API routes того же Next.js, там же MCP-эндпоинт `/mcp` | Один репозиторий, один контейнер |
| База | Postgres + pgvector в Docker, Drizzle ORM | Поиск по смыслу без отдельной векторной базы |
| AI | SecondGate через OpenAI SDK, модель в `LLM_MODEL` | Меняются только base URL, ключ и имя модели |
| Голос | `/audio/transcriptions` шлюза, запасной вариант Web Speech API | Работает и без модели речи в шлюзе |
| Вход | Auth.js с Google, только корпоративный домен | Решение команды; на сцене два профиля браузера для двух ролей |
| Хостинг | Docker Compose на сервере рядом с SecondStack, HTTPS через Caddy | Тот же compose, что у каждого локально |

## Одинаковый сетап на троих

У всех троих и их агентов одна и та же среда: репозиторий, `docker compose up` и один файл правил для агентов.

- **Один репозиторий.** Next.js-приложение, схема базы, миграции и seed лежат вместе.
- **Один `docker-compose.yml`.** Сервисы `db` (образ pgvector) и `app`. Локально можно поднимать только `db` и запускать `npm run dev`. На сервере тот же файл плюс Caddy для HTTPS.
- **Одинаковые данные.** `npm run db:reset` пересоздаёт базу и заливает один и тот же seed у всех.
- **Секреты.** В репозитории только `.env.example`; ключ шлюза и Google OAuth передаём через корпоративный менеджер паролей. Пока ключей нет, есть флаг `AUTH_DEV_LOGIN` для локального входа без Google.
- **Правила для агентов.** `AGENTS.md` в корне (и ссылка на него из `CLAUDE.md`): стек, команды, стиль, кто владеет какой папкой. Так три агента пишут одинаково и не правят чужое.
- **Схема базы у одного владельца.** Миграции пишет только он, остальные просят. Это главный источник конфликтов, когда пишут три агента сразу.
- **Маленькие merge request.** Вливаем в main часто, после каждого мержа сервер обновляется (скрипт `deploy.sh` или GitLab CI).

## AI-пайплайн

Каждый шаг с LLM возвращает строгий JSON по схеме, а не свободный текст: так интерфейс можно строить карточками, как в макете. Все вызовы идут через SecondGate (OpenAI-совместимый шлюз SecondStack): чат-модель, `/embeddings` и `/audio` для распознавания речи.

### Seek wisdom

1. **Ввод.** Голос записываем в браузере и отправляем в `/audio/transcriptions`; если в шлюзе нет модели речи, распознаём браузерным Web Speech API.
2. **Разбор запроса.** LLM делает краткую формулировку проблемы, область, теги, нужные навыки и тип нужды (инструмент, совет человека, автоматизация).
3. **Поиск.** Эмбеддинг формулировки ищем в трёх местах сразу: решения, люди (навыки + опыт) и чужие запросы. Поиск гибридный: векторная близость плюс совпадение тегов, по 5–10 кандидатов на тип.
4. **Рекомендация.** LLM получает запрос и кандидатов и выбирает один из четырёх путей: `use_solution`, `ask_expert`, `join_peers`, `build_new`. Она пишет вердикт, объяснение, три причины и текст кнопки. Выбирать можно только из переданных id, так Пифия не придумает несуществующего эксперта.
5. **Запись.** Запрос, найденное и рекомендация сохраняются: из них потом строятся Discoveries и «коллеги с той же проблемой».

### Share wisdom

1. **Извлечение.** Один вызов LLM возвращает три списка: навыки, опыт, решения. Любой из них может быть пустым.
2. **Нормализация.** Каждый навык сопоставляем со справочником по эмбеддингу, чтобы «Power BI» и «PowerBI дашборды» были одним навыком. Решения проверяем на похожие в каталоге.
3. **Кому пригодится.** Ищем открытые запросы, близкие по смыслу к извлечённому. LLM пишет одну строку «почему ему это полезно».
4. **Save & share.** Одна транзакция: навыки в профиль, опыт в профиль, решения в каталог, уведомления выбранным коллегам, запись в журнал вкладов для Pantheon.

### Discoveries

Запросы за период группируем по близости эмбеддингов (простая кластеризация по порогу). Кластер из 3 и более запросов становится Discovery: LLM даёт ему название и описание, мы считаем количество запросов, команды, покрытие (есть ли решение) и оценку потерянных часов.

### Build it with Pythia

LLM задаёт 3–4 уточняющих вопроса с вариантами ответа, затем собирает черновик спецификации и указывает, какие существующие решения можно переиспользовать. Черновик сохраняется как решение со статусом `draft`; дальше его можно отнести в Cowork Agent SecondStack.

## Модель данных

Хватит одного Postgres с расширением pgvector: 12 таблиц, а векторы лежат прямо в колонке `embedding` у навыков, опыта, решений и запросов. Отдельная векторная база не нужна.

| Таблица | Для чего | Ключевые поля |
| --- | --- | --- |
| `teams` | Команды и отделы для Discoveries | id, name |
| `users` | Сотрудники | id, sso\_subject, name, email, title, team\_id, avatar\_url, honorific («Keeper of the Data») |
| `skills` | Справочник навыков | id, name, category, aliases\[\], embedding |
| `user_skills` | Навыки человека в профиле | user\_id, skill\_id, level, source (declared / extracted / inferred), status (confirmed / suggested), contribution\_id |
| `experiences` | Опыт из проектов | id, user\_id, title, description, period, skill\_ids\[\], contribution\_id, embedding |
| `solutions` | Каталог: скиллы, агенты, автоматизации, инструменты | id, owner\_id, kind (skill / agent / automation / tool / mcp / doc), title, summary, how\_to\_use, url, visibility (everyone / team / private), status (draft / published), source (pythia / secondstack), external\_ref, usage\_count, embedding |
| `contributions` | Каждая отправка Share wisdom | id, user\_id, raw\_text, input\_mode (voice / text), extraction (jsonb), status (draft / saved), created\_at |
| `requests` | Каждый запрос Seek wisdom | id, user\_id, raw\_text, input\_mode, parsed (jsonb: формулировка, теги, тип нужды), recommendation (jsonb), status (open / resolved), discovery\_id, embedding |
| `request_matches` | Что нашла Пифия по запросу | request\_id, kind (solution / expert / peer), target\_id, score, reason, is\_recommended |
| `connections` | «Спросить эксперта», «объединиться», «использовал решение» | id, kind (ask\_help / join / used\_solution), from\_user\_id, to\_user\_id, request\_id, solution\_id, message, status (sent / accepted / helped) |
| `discoveries` | Повторяющиеся проблемы | id, title, summary, request\_count, team\_ids\[\], est\_hours\_lost, coverage (none / partial / covered), solution\_id, refreshed\_at |
| `wisdom_events` | Журнал вкладов для Pantheon и благодарностей | id, user\_id, kind (shared / helped / solution\_used / thanked), points, hours\_saved, ref\_type, ref\_id, from\_user\_id, note, created\_at |

Уведомления для демо можно не выносить в отдельную таблицу: это `connections` со статусом `sent` для получателя. Pantheon — это просто запрос `SUM(points)` по `wisdom_events` за месяц, квартал или всё время.

Черновая формула очков: поделился = 10, решение использовали = 5 за раз, помог коллеге = 20, поблагодарили = 3.

## API

Приложению хватит около двух десятков эндпоинтов; тяжёлые только два, с LLM.

| Эндпоинт | Экран | Что делает |
| --- | --- | --- |
| `POST /api/transcribe` | Ввод | Аудио в текст через шлюз |
| `POST /api/seek` | Seek wisdom | Разбор, поиск, рекомендация; стримит этапы, чтобы показать «The oracle is thinking…» |
| `GET /api/requests/:id` | Seek wisdom | Запрос с рекомендацией и найденным |
| `POST /api/connections` | Seek wisdom | Спросить эксперта, объединиться, отметить «использовал» |
| `POST /api/build/questions`, `POST /api/build/draft` | Build it | Уточняющие вопросы и черновик скилла |
| `POST /api/share/extract` | Share wisdom | Извлечение и «кому пригодится», ничего не сохраняет в профиль |
| `POST /api/share/:id/commit` | Share wisdom | Save & share с уже отредактированными данными |
| `GET /api/people`, `GET /api/people/:id` | Expertise | Поиск людей и профиль |
| `PATCH /api/me/skills/:id` | Expertise | Подтвердить или убрать найденный навык |
| `GET /api/discoveries`, `POST /api/discoveries/refresh` | Discoveries | Список и пересчёт кластеров |
| `GET /api/pantheon?period=` | Pantheon | Рейтинг, «Your standing», лента благодарностей |
| `POST /api/thanks` | Pantheon | Кнопка Thank |
| `GET /api/inbox` | Шапка | Входящие просьбы и уведомления |

Бонус, если останется время: отдать `seek` и `share` ещё и как MCP-сервер и зарегистрировать его в ControlTower. Тогда Пифию можно спросить прямо из чата SecondStack, и это сильный аргумент «мы на SecondStack» для жюри.

| Тема | Решение |
| --- | --- |
| Язык | TypeScript, одно Next.js-приложение |
| Хостинг | Docker Compose на нашем сервере рядом с SecondStack; Vercel и Supabase нельзя |
| Вход | Корпоративный Google |
| Модель | Та, что будет в шлюзе SecondStack; имя модели в переменной окружения |
| Данные | Реальные коллеги плюс синтетика для истории запросов и вкладов |

| Build it with Pythia | Пробуем создавать настоящий скилл (см. раздел ниже) |
| MCP-сервер | Делаем, Пифия доступна в чате SecondStack |
| Код | Скорее всего корпоративный GitLab, уточним 15 октября |

### Build it with Pythia по-настоящему

Демо: один человек рассказывает проблему, Пифия создаёт скилл, второй человек сразу его использует. Чтобы это точно сработало, делаем два пути.

1. **Скилл в формате Agent Skills.** После уточняющих вопросов LLM пишет `SKILL.md` (имя, описание, инструкции). Скилл сразу попадает в каталог PYTHIA со статусом `published`.
2. **Гарантированный путь: через наш MCP-сервер.** MCP PYTHIA отдаёт опубликованные скиллы как инструмент. Второй человек в чате SecondStack просит сделать задачу, модель берёт скилл из PYTHIA и выполняет. Это работает, даже если у SecondStack нет API для скиллов.
3. **Если получится: прямо в Cowork Agent.** Если в SecondStack есть API или папка для скиллов Cowork, публикуем `SKILL.md` туда же. Это проверяем утром 15 октября в docs.secondstack.ai.
